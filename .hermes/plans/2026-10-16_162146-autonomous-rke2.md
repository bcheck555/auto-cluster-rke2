# Autonomous Self-Building and Self-Healing RKE2 Cluster — Implementation Plan

## Goal
Build and verify a reproducible, secure RKE2 host-bootstrap and membership-management system, beginning with a read-only assessment of this Ubuntu/KVM host and an isolated, approval-gated VM lab.

## Current context / assumptions
- Workspace: `/var/github/auto-cluster`; Git repository exists, currently on `main` with no commits. Before implementation, inspect `git status`; create and switch to a feature branch before project edits, preserving any user work.
- This turn is plan-only. No host assessment commands, infrastructure changes, or implementation have been performed.
- The machine is described as Ubuntu Server 24.04.5 with KVM/libvirt, but actual OS, CPU virtualization flags, nested virtualization, RAM, disk, networks, VMs, pools, packages, firewall, and image/cloud-init availability are unverified.
- The host must never become a Kubernetes node. Existing VMs, networks, pools, host networking, and Hermes installation are protected; do not alter them without the user's explicit approval after presenting exact proposed changes.
- Assume initial test VMs can use one newly created isolated L2 network only after inspection shows it will not collide and the user approves host-affecting setup. Do not expose host libvirt credentials to guests.
- Verify current RKE2 release compatibility, registration behavior, ports, etcd membership/recovery procedures, and artifact verification against official documentation at implementation time. Pin exact versions and checksums in tracked config; do not invent a version in advance.
- Split-brain safety depends on a trusted pre-cluster bootstrap authority and fencing, not peer discovery alone. Lab authority may be a narrowly scoped host service, but production requires an external/redundant authority design before deployment.

## Architecture / proposed approach
Use a Go host agent with persistent identity and journaled idempotent state transitions, a Kubernetes membership controller for healthy-cluster reconciliation, and a narrowly privileged fencing service isolated on the development host. Treat an independent bootstrap authority as the only source of first-cluster authorization; use authenticated discovery only to find that authority/cluster, never as proof of authority or as a place to publish join secrets. Stage work through assessment, isolated lab, bootstrap/join, and then fencing-backed recovery; quorum loss always halts automation.

## Risks, tradeoffs, and open questions
- First-cluster authority is the core trust problem: without an external pre-established authority, simultaneous isolated hosts cannot safely decide which new cluster is authoritative. Lab host authority is a development-only trust root and single point of failure.
- Failure detection cannot distinguish a dead host from a network partition. Automatic replacement therefore requires positive, independently authenticated fencing; lack of fencing means fail closed.
- Embedded etcd quorum recovery is high risk. Quorum loss is manual recovery in the initial scope; automatic quorum reset remains disabled.
- RKE2 server-to-agent conversion is not assumed to be a native role-promotion operation. Promotion must be an audited stop/reconfigure/rejoin sequence based on verified release documentation and tested data handling.
- Five VMs may exceed available RAM, disk, CPU, or nested-virtualization capacity. Resource totals must be derived from the host assessment; use staged tests or defer VM gates if insufficient.
- Existing libvirt configuration, network ranges, storage pools, and host services may conflict. No host-impacting changes before exact proposal and user approval.
- Production Redfish/BMC authentication, redundant bootstrap authority, certificate issuance/rotation, and disaster recovery policy remain open and must be resolved before bare-metal production deployment.
- KubeVirt, Windows guests, distributed storage, and Multus are intentionally deferred until cluster membership and failure tests pass.
